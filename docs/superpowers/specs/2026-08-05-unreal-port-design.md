# Перенос клиента Tales of Pirate на Unreal Engine

**Дата:** 2026-08-05
**Статус:** этапы 0–2 и данные этапа 4 закрыты; остальное требует UE, Windows
или живых серверов — см. раздел «Граница».

## Цель

Заменить существующий клиент (C++23 поверх DirectX 9 движка MindPower3D) на клиент
Unreal Engine 5, сохранив совместимость с работающей серверной инфраструктурой.
Серверная логика переезжает на новый стек **позже, отдельным проектом** — на этом
этапе серверы не трогаются.

Вторая цель, ради которой затевается перенос: возможность добавлять в игру новый
3D-контент современными инструментами (Blender → UE), чего текущий движок не
позволяет без собственного экспортёра.

## Границы

**В объёме:**
- Оффлайн-конвертер проприетарных форматов MindPower3D в открытые.
- UE-проект: сетевой модуль, игровой слой, UI, импорт конвертированных ассетов.
- Совместимость с существующим протоколом WPacket/RPacket.

**Вне объёма (на этом этапе):**
- Любые изменения в `sources/Server/GameServer`, `sources/Dotnet/**`, БД, админке.
- Переписывание серверной логики под UE (отдельный будущий проект).
- Создание нового арта. Пайплайн для него готовится, сам контент — нет.

**Не переносится вообще:**
- `Client/src/Gui` (61 274 строки) — заменяется на UMG.
- `Client/src/App` (10 481) — game loop, окно, ввод даёт UE.
- `Client/src/Audio` (1 514) — заменяется на UE Audio.
- `sources/Engine` как рантайм — MindPower3D остаётся только как источник знаний
  о форматах файлов.

## Выбранный подход

Из трёх рассмотренных вариантов выбран **гибрид**:

- **Переиспользуется дословно** то, где переписывание даёт риск без выгоды:
  бинарный протокол (`CommandMessages.h` — 13 864 строки, ~1300 команд,
  сериализация MessagePack) и парсеры файловых форматов.
- **Переписывается** то, где legacy-код — обуза: состояние мира, завязанное на
  DX9-рендер и самописный GUI.
- **Выбрасывается** движковый обвес, который UE даёт из коробки.

Отвергнутые варианты:

- *Тонкий UE-фасад над legacy-ядром.* Быстрее до первого запуска, но `Scene`
  пронизан вызовами в GUI и рендер MindPower3D — «чистым» модулем он не является.
  Результат — два параллельных мира состояния и вечная синхронизация между ними;
  будущий переезд сервера на UE-стек из такой архитектуры не делается.
- *Полное переписывание в UE-идиомах.* Теряется гарантия совместимости с сервером:
  12 696 строк протокольного кода, переписанные вручную, дадут десятки тонких
  расхождений в раскладке байтов, ловящихся только в рантайме.

## Архитектура

Три независимых артефакта:

```
tools/AssetConverter/          оффлайн-утилита, без UE и без DirectX
        │  .lgo/.lmo/.lab/.obj/.map  →  glTF 2.0 + JSON-манифесты
        ▼
CorsairsUE/                    UE 5.x проект
  Source/CorsairsNet/          протокол перенесён 1:1 + UE-транспорт
  Source/CorsairsGame/         игровой слой, переписан
  Source/CorsairsImport/       editor-модуль: манифест → UE Level
  Content/                     результат конвертации
        │  WPacket/RPacket поверх TCP
        ▼
существующие серверы           БЕЗ ИЗМЕНЕНИЙ
  GameServer (C++), Account/Gate/Group (F#), Admin.Web (C#)
```

### Почему конвертер вынесен из UE

Как editor-плагин он тянет зависимость от запущенного редактора. Требуется
пакетный прогон по 6702 моделям, отладка на отдельных файлах и покрытие тестами —
это даёт отдельная консольная утилита, а не плагин. UE получает только
`CorsairsImport`, импортирующий уже готовые glTF и манифесты.

### Почему glTF, а не FBX

glTF 2.0 — открытая спецификация, писать из C++ можно вручную или через `tinygltf`.
FBX требует проприетарного SDK Autodesk. UE импортирует оба через Interchange
одинаково. Скелетные анимации, скиннинг и иерархия костей выражаются в glTF
полностью.

### Почему манифесты сцен — JSON, а не `.umap`

Формат уровней UE бинарный и версионированный; генерировать его вне движка
ненадёжно. Конвертер пишет читаемый манифест («на карте `garner` в точке X,Y,Z
модель `tree_01` с поворотом R, масштабом S»), а `CorsairsImport` расставляет
акторы средствами UE API. Манифест дополнительно можно продиффать глазами.

## Конвейер ассетов

### Препятствие: движковые загрузчики непереносимы

Движковые исходники нельзя использовать как библиотеку конвертера по двум
независимым причинам:

1. `Model/lwExpObj.h` и `Core/lwITypes2.h` подключают `lwDirectX.h`, `stdafx.h` и
   оперируют `DWORD` / `D3DPRIMITIVETYPE` / `D3DVERTEXELEMENTX`;
   `Map/SceneFileLoaders.h` — `d3dx9math.h`. Подключение
   `sources/Libraries/DirectX/include` на x64 запрещено (C2733 — конфликт с
   `winnt.h` современного Windows SDK, см. `CLAUDE.md`). Зависимость транзитивно
   тянет весь движковый core, а не отдельные структуры.
2. Разработка ведётся на macOS ARM64, где нет ни MSVC, ни Windows SDK, ни
   DirectX. Движковый код на этой машине не собирается в принципе.

**Решение:** `AssetConverter` — самостоятельный кроссплатформенный парсер на
чистом C++23 (собирается clang на macOS и MSVC на Windows, без внешних
зависимостей). Движковые исходники — `Asset/AssetLoaders.cpp`, `Model/lwExpObj.h`,
`Core/lwITypes.h`, `Core/lwITypes2.h` — используются как **спецификация
бинарного формата**, а не как код.

Раскладка `.lgo` (проверена на `Client/model/character/0066000000.lgo`,
18 044 байта):

```
[4]    version DWORD           0x0000 | 0x1000..0x1005
[116]  lwGeomObjInfoHeader     id, parent_id, type, mat_local[64],
                               rcci[16], state_ctrl[8],
                               mtl_size, mesh_size, helper_size, anim_size
[mtl_size]     блок материалов  mtl_num DWORD + lwMtlTexInfo[mtl_num] (по 1004 б)
[mesh_size]    блок геометрии   lwMeshInfoHeader[128] + массивы по FVF
[helper_size]  блок helper'ов   dummy / box / mesh / bbox / bsphere
[anim_size]    блок анимации    UV- и opacity-анимация
[остаток]      трейлер, игнорируется
```

Инвариант, лежащий в основе тестирования: `4 + 116 + сумма четырёх *_size`
не превосходит размер файла, а каждый блок-парсер обязан прочитать **ровно**
объявленное для него число байт. Это строже проверки в оригинальном
`LgoLoader::LoadEx`, которая сверяет только итог по файлу.

Размеры фиксированных структур проверяются `static_assert` в коде конвертера:
`lwMtlTexInfo` = 1004, `lwTexInfo` = 208, `lwMaterial` = 68,
`lwMeshInfoHeader` = 128, `lwSubsetInfo` = 16, `lwBlendInfo` = 20. Это защита от
того же класса ошибок, из-за которого в `lwTexInfo` появилось поле
`_reserved_data`: указатель `void*` менял размер между x86 и x64 и ломал разбор
файлов.

### Извлекаемые данные

| Источник | Что извлекается | Выход |
|---|---|---|
| `.lgo` | `lwMeshInfo`: вершины, нормали, до 4 UV-наборов (`texcoord0..3_seq`), индексы, `blend_seq` (веса скиннинга), `bone_index_seq`, `subset_seq` (материальные подсеты). `HelperInfo`: `dummy_seq` / `box_seq` / `bbox_seq` / `bsphere_seq` — точки крепления оружия и эффектов. `lwMtlTexInfo`: имена текстур, режим прозрачности (`lwMtlTexInfoTransparencyTypeEnum`) | `.gltf` + `.bin` |
| `.lmo` | `lwModelInfo` / `lwModelNodeInfo` — дерево узлов со ссылками на geom-объекты | `.gltf` со сценой-иерархией |
| `.lab` | `lwAnimDataBone`: `_base_seq` (имя, `id`, `parent_id` → иерархия), `_invmat_seq` (inverse bind matrices), `_key_seq` (ключи по кадрам; `_key_type` = `BONE_KEY_TYPE_MAT43` / `MAT44` / `QUAT`), `_frame_num`, `_dummy_seq` | glTF skin + animation |
| `.obj` / `.rbo` | `SFileHead` (версия 600, легаси 500 конвертируется при чтении), таблица секций `SSectionIndex`, `SSceneObjInfo`: `sTypeID`, `nX`, `nY`, `sHeightOff`, `sYawAngle`, `sScale` | JSON-манифест сцены |
| `.map` (`MPMap`) | тайловая сетка, высоты, `_sTileRegionAttr` — атрибуты проходимости | heightmap PNG16 + attribute map + JSON |
| `.eff` / `.par` | параметры партиклов и эффектов | JSON (для ручного воссоздания в Niagara) |
| PNG / DDS | текстуры | PNG как есть; DDS → PNG либо импорт DDS напрямую |

### Имена текстур не совпадают с файлами на диске

Внутри `.lgo` имена текстур записаны с расширением `.BMP` — проверено на
`Client/model/character/0066000000.lgo`, который ссылается на
`0066000000.BMP`. Фактический файл — `Client/texture/character/0066000000.png`.
Проект когда-то перешёл с BMP на PNG, не переписывая модели; движок ищет
текстуру, игнорируя расширение.

Любой резолвер текстур обязан искать по имени без расширения, перебирая
существующие варианты (`.png`, `.dds`, `.jpg`). Прямое сопоставление по полному
имени не найдёт ни одной из 12 762 текстур.

### Атрибуты проходимости

Сервер считает движение по своей копии карты. Если UE-клиент построит навигацию
самостоятельно (NavMesh по геометрии), она разойдётся с серверной, и игрока будет
«отбрасывать» назад при рассинхроне. Поэтому `_sTileRegionAttr` конвертируется и
остаётся источником истины; UE-навигация строится по нему, а не по мешам.

### Валидация

1. **Golden-тесты.** Конвертер и legacy-loader читают один файл; сверяются
   `vertex_num`, `index_num`, `bone_num`, `frame_num`, bounding box. Расхождение —
   баг конвертера.
2. **Визуальная проверка в Blender** (через Blender MCP): открыть конвертированный
   glTF, проверить скелет, прогнать анимацию, поймать перевёрнутые нормали и
   вывернутые кости.
3. **Пакетный прогон.** Все 6702 `.lgo` через конвертер, отчёт по `LgoLoadStatus`
   (`Ok` / `OkWithTrailingData` / `VersionUnknown` / `HeaderTruncated` /
   `BlockSizesInconsistent` / `ParseFailed`). Битые файлы в датасете есть
   (например, `Client/texture/effect/sdasd`), и отчёт должен их называть, а не
   молча пропускать.

## Сетевой слой

Модуль `Source/CorsairsNet`.

**Переносится как есть:** `CommandMessages.h`, `CommandNames.h`, mpack,
`BinaryIO.h`, `PacketPool.h`, `Packet.h`, `MsgpackUtil.h`, криптография из
`Client/src/Crypto`.

**Пишется заново:** транспорт. Legacy `Client/src/Net/Transport/Connection`
(сырые сокеты, собственные `std::thread`, C-style include guard, `m_`-префиксы)
заменяется на `FSocket` внутри `FRunnable`. Входящие пакеты складываются в
потокобезопасную очередь и разбираются в GameThread.

**Проверка до всякой графики:** консольный клиент на этом модуле логинится к
живым Account → Gate → Group → Game и печатает поток событий мира. Успех здесь
доказывает совместимость; дальше остаётся только вопрос отображения.

## Игровой слой

| Класс | Ответственность |
|---|---|
| `UCorsairsGameInstance` | сессия, соединение, состояние логина; переживает смену уровня |
| `ACorsairsPlayerController` | ввод, клики по миру, отправка команд намерения |
| `ACorsairsCharacter` | `USkeletalMeshComponent`, слоты экипировки по helper-dummy из `.lgo` |
| `UCorsairsWorldState` | реестр видимых сущностей, приём `CMD_MC_*`, интерполяция |
| UMG-виджеты | UI с нуля |

**Клиент не принимает решений.** Он отправляет намерение (`Cmd_BeginMove`,
`Cmd_BeginSkill`), сервер отвечает (`CMD_MC_NOTIACTION` при успехе,
`CMD_MC_FAILEDACTION` при отказе), клиент проигрывает результат. Локальное
предсказание — только визуальное сглаживание поверх этой схемы и только после
того, как базовый цикл заработает.

Существующий `Client/src/Scene` (33 220 строк) при переписывании используется как
**построчная спецификация поведения**, а не как источник для механического
переноса.

## Граница: что сделано и где нужен Unreal Engine

Работы делятся по тому, какая машина для них нужна. Всё, что не требует UE,
выполнено на macOS и закрыто.

**Закрыто (не требует UE, Windows или живых серверов):**

- Этап 0 — каркас конвертера.
- Этап 1 — геометрия: все версии `.lgo`, модели `.lmo`, helper-блоки и точки
  крепления.
- Этап 2 — скелеты и анимации `.lab`: иерархия костей, обратные bind-матрицы,
  дорожки на 30 FPS. 18 640 костей и 37 280 каналов, ноль структурных проблем.
- Этап 4, часть «данные» — террейн, проходимость, регионы и манифесты объектов.

**Делается на macOS, нужен только установленный софт:**

- Unreal Engine 5 — **нативная сборка под Apple Silicon**, эмуляция Windows не
  нужна и вредна (официальной сборки UE под Windows on ARM не существует).
  Отсюда: модуль `CorsairsImport`, импорт Landscape из `.r16`, навигация по
  `.block.raw`, привязка мешей к скелетам, UI на UMG, игровой слой.
- Серверы Account / Gate / Group / Admin.Web — F# и C# на `net10.0`,
  кроссплатформенные; в `Platform.Database` подключены провайдеры SQLite и
  PostgreSQL помимо MSSQL, поэтому Windows-стек им не нужен. Хватает, чтобы
  дойти до логина и списка персонажей.
- Blender для визуальной проверки моделей — нативно под Apple Silicon.

**Требует Windows (и именно x86, не ARM):**

- `GameServer` — C++ под MSVC, ODBC и MSSQL с `Trusted_Connection=Yes`.
  Сборок SQL Server под ARM не существует, поэтому виртуалка на Apple Silicon
  здесь не помогает.
- Вход в игровой мир и, следовательно, полный вертикальный срез (этап 5).
- Запуск legacy-клиента как эталона поведения.

WSL задачу не решает: в нём нет MSVC, Windows SDK и DirectX, а .NET-серверы и
так идут на macOS нативно.

**Не выполнено:** визуальная проверка моделей в Blender — MCP не смог
подключиться, Blender не был запущен. Вместо неё сделаны численные проверки:
согласованность нормалей и winding'а (300 из 300 треугольников на контрольной
модели) и валидация иерархии всех 670 скелетов.

## Анимации: что мешает и что нужно сделать

Скелеты и дорожки конвертируются (670 файлов `.lab`, 78 узлов и 56 костей в
типовом), но применить их к телу персонажа пока нельзя. Причина в том, как
устроены исходные данные:

- **Скелет живёт в `.lab`**: настоящие имена костей (`Bip01 Pelvis`), иерархия
  через `ParentId`, обратные bind-матрицы. Индекс кости в массиве совпадает с
  её `Id` — код движка сравнивает `ParentId` именно с индексом.
- **Меш в `.lgo` знает только глобальные номера костей.** В glTF они выходят
  плоским списком с именами вида `bone_6`, и таких суставов у части тела всего
  три против 56 в скелете.

Interchange строит скелет по тому, что видит в файле меша, то есть из трёх
костей без иерархии. Дорожка, привязанная к 56-костному скелету из `.lab`, к
нему не применяется.

**Что нужно.** Модель персонажа должна выходить одним glTF, содержащим полную
иерархию костей с настоящими именами и обратными bind-матрицами, а `JOINTS_0`
ссылаться на позиции в этом списке: `blend.Index[k]` -> `BoneIndices[...]` ->
номер кости, он же индекс сустава.

**Откуда брать скелет.** Имя выводится из имени скина: `0001000000.lgo`
соответствует `0001.lab` — первые четыре цифры. Соглашение проверено на всём
наборе: разрешается для 2941 модели персонажа из 4913, включая все играбельные
типы. Для остальных 982 скелета нет, ещё 990 имён не следуют схеме; такие
модели остаются без привязки, и это нужно отражать в отчёте, а не замалчивать.

Писать результат следует в отдельный файл, не трогая существующий вывод: пока
привязка не подтверждена импортом, работающий конвейер ломать нельзя.

карте, позиция клиента совпадает с серверной; **6** — работающий пайплайн
Blender → UE.

Вся серверная связка (GameServer на C++ плюс Account, Group и Gate на .NET)
работает на macOS без Windows; поднимается через `scripts/dev/run-stack.sh`.

Не закрыто:

- **анимации** — скелетные меши и дорожки импортированы, но не связаны;
  разбор причины и план в разделе «Анимации» выше;
- **экран входа** — состояние сессии показывается, полей ввода нет: учётные
  данные лежат в настройках режима игры;
- **материалы** — те, что построил Interchange по базовой текстуре;
  пересборка средствами UE не начата;
- **текстуры рельефа** — слои лежат в `TileInfo` каждой клетки, разбор
  отдельной задачей.

Этап 0 предшествует всем. Этапы 1, 2 и 3 после него независимы друг от друга и
могут идти в любом порядке; этап 4 требует 1, этап 5 требует 2, 3 и 4.

**Этот документ описывает программу работ целиком, а не один цикл реализации.**
Каждый этап получает собственный план реализации. Первый план покрывает этапы
0 и 1 — до этого момента слишком мало известно о реальном состоянии данных,
чтобы осмысленно планировать дальше: отчёт пакетного прогона по 6702 файлам
может изменить оценку этапов 2 и 4.

## Тестирование

- **Конвертер:** golden-тесты против legacy-loader'а на фиксированном наборе
  файлов; пакетный прогон с отчётом по статусам.
- **Сеть:** консольный клиент против живых серверов; проверка round-trip
  сериализации отдельных команд.
- **Игровой слой:** ручная проверка в UE-вьюпорте на этапах 2 и 5; сверка позиции
  клиента с серверной как численный критерий этапа 5.
- Существующий legacy-клиент остаётся рабочим эталоном для сравнения поведения на
  всём протяжении работ.

## Обработка ошибок

- Конвертер на битом файле **не падает и не молчит**: пишет статус в отчёт и
  продолжает пакет. Итоговый отчёт перечисляет все незагруженные файлы с причиной.
- Сетевой модуль на неизвестной команде логирует её код и продолжает; на разрыве
  соединения возвращает пользователя на экран логина.
- Согласно `CLAUDE.md`, `try/catch` не добавляется без явного согласования —
  ошибки диагностируются через возвращаемые статусы (`LgoLoadStatus` и аналоги).

## Среда разработки

Основная машина — **macOS ARM64** (Apple clang 21). Существующий C++-код проекта
на ней не собирается: он требует MSVC, Windows SDK и DirectX.

Следствия:

- `AssetConverter` пишется кроссплатформенным (CMake + C++23, без внешних
  зависимостей) и разрабатывается на macOS. Это не уступка, а требование: без
  него весь этап 1 упирается в наличие Windows-машины.
- UE-проект разрабатывается там, где стоит Unreal Engine. Для этапов 0–1 UE не
  нужен вообще — конвертер от него не зависит.
- Legacy-клиент как эталон для сравнения доступен только на Windows. Проверки,
  требующие его запуска, планируются с этим ограничением.

## Соглашения

Действуют правила из `CLAUDE.md`: namespace `Corsairs::*`, `PascalCase` для
методов, `_camelCase` для полей класса, `PascalCase` для полей struct,
`enum class` с фиксированным underlying-типом, `#pragma once`, типы фиксированной
ширины из `<cstdint>`, `std::chrono` для времени, обязательные фигурные скобки.

Новый код конвертера — `Corsairs::Tools::AssetConverter`. UE-модули следуют
соглашениям Unreal (`F`/`U`/`A`-префиксы) — это диктуется движком и является
законным исключением, как WinAPI-колбэки.

### Игровые данные для этапа 4: где они лежат

Связь `modelId` из манифеста карты с конкретным файлом модели задаётся таблицей
**`scene_objects`** (см. `SceneObjRecordStore` в
`sources/Libraries/common/src/World/`). Той же природы связь модели персонажа со
скелетом: клиент берёт `pInfo->Model` и формирует имя `{:04}.lab`.

Наполненная база — **`databases/gamedata.sqlite`** (6.6 МБ), её и открывает
GameServer. Файл `server/GameServer/gamedata.sqlite` весит 0 байт и никем не
используется; ориентироваться на него нельзя — именно он однажды был принят за
отсутствие данных и породил ложный блокер этапа.

Что там есть:

| Таблица            | Записей | Назначение                                          |
|--------------------|---------|-----------------------------------------------------|
| `scene_objects`    | 649     | `data_name` → файл модели, например `by-bd001.lmo`  |
| `character_models` | 3       | `character_type` → `bone` (`.lab`) и до пяти `.lgo` |
| `characters`       | 1650    | `model` — числовой индекс, разворачивается в `{:04}.lab` |

Конвейер к этапу готов: манифест содержит `modelId`, имена суставов в скиннинге
несут глобальные id костей, сопоставление модель → файл доступно.

### Что осталось за пределами конвертации

- **Эффекты и партиклы** (`.eff` — 1233, `.par` — 1034). Конвертер их не
  разбирает намеренно: в движке уже есть `EffectLoader::ExportToYaml`
  (`sources/Engine/Effect/EffectYaml.cpp`), то есть экспорт формата написан.
  Дублировать его в конвертере незачем — достаточно прогнать существующий
  экспорт на Windows. Сами эффекты по решению из спеки воссоздаются в Niagara.
- **Текстуры** (12 762 PNG, 924 DDS) копируются как есть, конвертация не нужна.
- **`.rbo`** — текстовый sidecar «больших объектов». В датасете все встреченные
  файлы пустые, поэтому парсер не писался.

### Две раскладки формата

Первый прогон дал 6581 `OK` и 91 `VERSION_UNSUPPORTED`; вторая раскладка была
реализована следом, и сейчас поддержаны обе.

**Современная (`version` 0x1004–0x1005), 6581 файл.** Блоки идут подряд без
вложенных версий; материал — 1004 байта; в блоке геометрии массивы в порядке
*вершинные элементы → позиции → нормали → UV → цвета → скиннинг → индексы →
подсеты*; индексы костей 32-битные; скиннинг определяется полем `BoneIndexNum`.

**Легаси (`version` 0x0000), 91 файл** — 41 в `item/`, 36 в `character/`, 14 в
`effect/`. Отличия, все три существенные:

1. В начале **каждого** блока лежит вложенная версия (`DWORD`), и блок читается
   по ней, а не по внешней.
2. Материал занимает 1028 байт: нет полей `Opacity`/`TranspType`, другой формат
   render states (`RenderStateValue[2][8]` вместо `RenderStateAtom[8]`) и текстур
   (`TexInfoV0`, 208 байт).
3. В блоке геометрии **подсеты читаются первыми**, а индексы костей —
   однобайтовые; наличие скиннинга определяется флагом FVF `LASTBETA_UBYTE4`
   (0x1000), а не полем `BoneIndexNum`.

Заголовок объекта у обеих раскладок одинаковый — те же 116 байт.

Версии `0x1000`–`0x1003` в датасете **отсутствуют** и намеренно не реализованы:
парсер вернёт для них `VERSION_UNSUPPORTED`. Если такие файлы появятся, работа
понадобится в блоке геометрии (заголовок `lwMeshInfo_0003`) — материалы у них
уже читаются современным путём.

FVF, встречающиеся в легаси-файлах: `0x0112` (64 файла), `0x0152` — с цветом
вершин (24), `0x1118` — со скиннингом (3).

## Открытые вопросы

Решаются в момент, когда до них дойдёт очередь, и не блокируют этапы 0–3:

1. **Судьба Lua.** В клиенте 40 `.lua`-файлов и 3 250 строк биндингов
   (`Client/src/Script`). Варианты: воссоздать логику на C++/Blueprints либо
   поднять LuaJIT внутри UE. Решается на этапе 5, когда станет видно, сколько
   игровой логики реально живёт в скриптах.
2. **Судьба эффектов.** 2 267 файлов `.eff`/`.par`. Конвертер извлекает параметры
   в JSON, но автоматическая генерация Niagara-систем из них может оказаться
   нерентабельной по сравнению с ручным воссозданием ключевых эффектов.
   Решается после этапа 1.
3. **Версия UE.** Фиксируется на этапе 0: берётся последняя стабильная (не
   Preview) версия 5.x на момент создания проекта, и дальше **не меняется** до
   завершения этапа 5. Апгрейд движка посреди переноса ломает воспроизводимость
   проверок.
