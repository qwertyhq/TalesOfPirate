## 1. Что уже готово

Всё влито в `main`. Ключевые коммиты — от `60dc82ed` до `7f8c84d0`.

`tools/AssetConverter` — самостоятельная кроссплатформенная утилита на C++23 без
внешних зависимостей. Конвертирует **весь** клиентский датасет:

| Каталог | Файлов | Успешно | Что делает |
|---|---|---|---|
| `Client/model` | 7311 | 7311 | `.lgo` и `.lmo` → glTF 2.0: геометрия, скиннинг, материалы, точки крепления |
| `Client/animation` | 670 | 670 | `.lab` → скелет, skin, анимация на 30 FPS |
| `Client/map` | 99 | 99 | `.map` → heightmap/проходимость, `.obj` → манифест |
| `Client/effect` | 7 | 7 | геометрия эффектов |
| `Client/texture` | 28 | 28 | геометрия в каталоге текстур |
| **Всего** | **8115** | **8115** | ноль ошибок |

72 теста, чистая сборка без предупреждений.

**Проверить, что всё на месте:**

```bash
cd tools/AssetConverter
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug && cmake --build build
./build/AssetConverterTests          # ожидается: 72 тестов, провалено 0
```

**Сконвертировать датасет заново:**

```bash
# --textures включает резолвинг текстур и копирование их в out/model/textures/
./tools/AssetConverter/build/AssetConverter Client/model     out/model     --textures Client/texture --report model.csv
./tools/AssetConverter/build/AssetConverter Client/animation out/animation --report anim.csv
./tools/AssetConverter/build/AssetConverter Client/map       out/map       --report map.csv
```

Код возврата 0 означает, что ошибок нет. Отчёт CSV перечисляет каждый файл со
статусом — ни один не пропускается молча.

## 2. Где что можно делать: карта сред

Это главный вывод, и он не такой, как казалось вначале.

| Работа | macOS (Apple Silicon) | Windows |
|---|---|---|
| `AssetConverter` | **да**, основная среда разработки | да, MSVC + CMake |
| Unreal Engine 5, редактор | **да, нативно на arm64** | да |
| Импорт ассетов в UE, UI, игровой слой | **да** | да |
| Account / Gate / Group (F#, `net10.0`) | **да**, через `dotnet run` | да |
| Admin.Web (Blazor) | **да** | да |
| Blender для проверки моделей | **да**, нативно | да |
| `GameServer` (C++, MSVC, ODBC) | **нет** | только здесь |
| MSSQL с `Trusted_Connection=Yes` | **нет** | только здесь |
| Запуск legacy-клиента как эталона | **нет** | только здесь |

### Про WSL

WSL **не решает** задачу. В нём нет MSVC, нет Windows SDK, нет DirectX и нет
Unreal Engine для Linux в том виде, в каком нужен этот проект. Единственное, что
в WSL пошло бы, — .NET-серверы, но они и так работают на macOS нативно. Смысла
заводить WSL ради этого проекта нет.

### Про эмуляцию Windows на Apple Silicon

**Плохая идея для UE.** Официальной сборки Unreal Engine под Windows on ARM не
существует; в виртуалке редактор пошёл бы через x86-эмуляцию и с урезанным
доступом к GPU. UE — это шейдерная компиляция и тяжёлая графика, в такой
конфигурации работать невозможно.

**Правильный ход:** ставить Unreal Engine для macOS — он нативный под Apple
Silicon.

Виртуалка с Windows оправдана **только** ради `GameServer` и MSSQL, и даже там
есть засада: сборок SQL Server под ARM не существует, а Windows 11 ARM в
Parallels — это ARM. Для GameServer нужна либо настоящая x86-машина с Windows,
либо удалённый сервер.

## 3. Что делать дальше на macOS (не требует Windows)

Порядок — по возрастанию зависимости от предыдущего шага.

### Шаг A. Unreal Engine и проект — ГОТОВО

**UE 5.8.1 установлен** в `/Users/Shared/Epic Games/UE_5.8` (нативная сборка под
Apple Silicon). Версию не менять до конца этапа 5: апгрейд движка посреди
переноса ломает воспроизводимость проверок.

**Проект `CorsairsUE/` создан и собирается.** Четыре модуля по схеме спеки:
`CorsairsNet` (Runtime, PreDefault), `CorsairsGame` (Runtime), `CorsairsUE`
(первичный игровой модуль), `CorsairsImport` (Editor).

```bash
"/Users/Shared/Epic Games/UE_5.8/Engine/Build/BatchFiles/Mac/Build.sh" \
    CorsairsUEEditor Mac Development -project="$PWD/CorsairsUE/CorsairsUE.uproject"
```

Сборка занимает около 20 секунд. `Content/`, `Binaries/`, `Intermediate/` и
`Saved/` в git не попадают.

### Шаг B. Импорт конвертированных ассетов — ПРОВЕРЕНО

```bash
"/Users/Shared/Epic Games/UE_5.8/Engine/Binaries/Mac/UnrealEditor-Cmd" \
    "$PWD/CorsairsUE/CorsairsUE.uproject" -run=pythonscript \
    -script="$PWD/CorsairsUE/Scripts/import_assets.py <каталог-gltf> /Game/Converted" \
    -unattended -nosplash -nullrhi
```

Результат импорта контрольных файлов — ноль ошибок Interchange:

| Исходник | Что создаёт UE |
|---|---|
| `0066000000.lgo` (скиннинг) | SkeletalMesh + Skeleton + PhysicsAsset + Material + Texture |
| `04090084.lgo` (без костей) | StaticMesh + Material + Texture |
| `0301.lab` (скелет) | Skeleton + AnimSequence + PhysicsAsset |

**Раскладку каталогов при импорте нарушать нельзя.** URI текстуры в glTF —
`../textures/<категория>/<файл>`, то есть glTF должен лежать в
`<выход>/<категория>/`, а текстуры в `<выход>/textures/<категория>/`. Если
сплющить структуру, UE не найдёт текстуры.

Контрольные файлы, на которых всё проверялось при разработке:

- `Client/model/character/0066000000.lgo` — 250 вершин, 300 треугольников,
  1 материал, текстура `0066000000.BMP`, bounding sphere;
- `Client/model/character/04090084.lgo` — 5 точек крепления (`dummy_0`…`dummy_4`);
- `Client/animation/0301.lab` — 34 кости, 170 кадров, 8 dummy, ключи QUAT,
  корневая кость `Bip01`, длительность 5.633 с.

**Если геометрия окажется зеркальной** — искать в `GltfWriter.cpp`: инверсия Z и
смена порядка обхода треугольника обязаны применяться **вместе**. Численная
проверка уже есть: нормали граней согласованы с нормалями вершин у 300 из 300
треугольников контрольной модели.

**Если анимация вращается не в ту сторону** — смотреть
`ConvertQuaternionToGltf`: под отражением `(x,y,z,w) → (−x,−y,z,w)`, отрицаются
X и Y, а не Z.

**Проверить любой конвертированный файл сторонним импортёром:**

```bash
/Applications/Blender.app/Contents/MacOS/Blender --background --factory-startup \
    --python tools/AssetConverter/scripts/validate_gltf.py -- <файл.gltf>
```

Скрипт печатает счётчики вершин, костей, материалов, ключей анимации и вершин
со скиннингом. Прогнан на 45 случайных файлах — ноль ошибок импорта.

**Икосфера на 42 вершины в импорте скелета — не баг.** Blender подставляет
объект-заглушку для `skin`, на который не ссылается ни один меш. Такой skin в
файлах анимаций присутствует намеренно: он несёт обратные bind-матрицы, а они
не выводятся из дорожки — численно показано, что bind-поза отличается от позы
первого кадра. Заглушка безвредна и удаляется.

### Шаг C. Landscape и навигация

Из `<карта>.height.r16` — импорт Landscape (UE читает сырой r16 напрямую).
Метаданные в `<карта>.terrain.json`: размер сетки, кодировка высоты
(`uint16 = (rawHeight + 128) * 256`), единица — 10 см.

**Навигацию строить по `<карта>.block.raw`, а не по NavMesh из геометрии.**
Это 4 байта на тайл — флаги проходимости по четвертям. Сервер считает движение
по своей копии карты; любое расхождение проявится как «резинка», когда игрока
отбрасывает назад.

### Шаг D. Объекты сцены

`<карта>.objects.json` — список размещённых моделей: `modelId`, `type`, `x`, `y`,
`heightOff`, `yaw`, `scale`. На `garner` их 50 017. Координаты остались в
исходных целых единицах карты — пересчёт в единицы UE делается при импорте, где
известен масштаб мира.

**Связь `modelId` → файл модели заблокирована отсутствием данных.** Она живёт в
таблице `scene_objects` базы `server/GameServer/gamedata.sqlite`, поле
`_dataName` (см. `SceneObjRecordStore`). В этом чекауте база весит 0 байт.
Той же природы связь модели со скелетом: клиент берёт `pInfo->Model` и строит
имя `{:04}.lab`.

Нужен рабочий `gamedata.sqlite` с боевого сервера. До этого объекты карты
разместить нельзя, а скиннинг мешей не с чем связать — хотя сами данные
скиннинга уже в glTF, и имена суставов несут глобальные id костей.

Координаты в манифесте — **мировые**, пересчёт из относительных уже сделан
(в файле они относительны началу секции, множитель `sectionSize * 100`).

### Шаг E. Сетевой слой, частично

**.NET 10.0.302 уже установлен** в `~/.dotnet` (через `dotnet-install.sh`, без
sudo — установка cask'ом требует пароль). Добавьте в PATH:

```bash
export PATH="$HOME/.dotnet:$PATH"
```

Проверено на macOS ARM64: Account, Gate, Group и Admin.Web собираются с нулём
ошибок, 507 тестов `Platform.Network` проходят. Для этого пришлось убрать из
`Corsairs.Platform.Msgpack.csproj` условие `OS != Windows_NT`, подменявшее
TargetFramework на снятые с поддержки фреймворки (коммит `5891b410`); на
Windows поведение не изменилось.

Поднять серверы, которые не требуют Windows:

```bash
dotnet run --project sources/Dotnet/Servers/Account/Corsairs.AccountServer  # TCP:9958
dotnet run --project sources/Dotnet/Servers/Gate/Corsairs.GateServer        # TCP:1973
dotnet run --project sources/Dotnet/Servers/Group/Corsairs.GroupServer      # TCP:9957/9956
```

В `Platform.Database` подключены провайдеры **SQLite и PostgreSQL** помимо
MSSQL — то есть для локальной разработки MSSQL не нужен.

С этими тремя серверами реально дойти до **логина и списка персонажей**. Вход в
мир требует `GameServer`, а он только на Windows.

## 4. Что требует Windows

Единственная область — `GameServer` и всё, что от него зависит.

- Сборка: `msbuild sources/talesofpirates.sln /p:Configuration=Debug /p:Platform=x64`
  (VS 2026 Preview, toolset v145, x64-only).
- БД: строка подключения захардкожена в `GameDB.cpp` и `TradeLogDB.cpp` —
  `DRIVER={ODBC Driver 17 for SQL Server};SERVER=localhost;DATABASE=gamedb;Trusted_Connection=Yes;`.
- Legacy-клиент как эталон поведения: `Game.exe pKcfT0PcaX` (аргумент-пароль
  обязателен), рядом должны лежать `SDL3.dll` и `SDL3_mixer.dll`.

Что здесь делать:

1. Поднять MSSQL и GameServer, убедиться, что связка Account → Gate → Group →
   Game работает со старым клиентом.
2. Этап 3: консольный клиент на переносимом коде `CorsairsNet` логинится к живым
   серверам и печатает поток событий мира. Это доказывает совместимость
   протокола до всякой графики.
3. Этап 5: сверка позиции UE-клиента с серверной — численный критерий готовности
   вертикального среза.

**Проверить перед сборкой на Windows:** конвертер там ещё не собирался ни разу.
Ожидаемых проблем нет — `/utf-8`, флаги для всех целей и нормализация путей уже
добавлены (коммит `981cc97a`), — но первый прогон `AssetConverterTests` на MSVC
стоит сделать сразу и убедиться, что 64 теста проходят и русский текст в выводе
читаемый. Консоль Windows для этого должна быть в UTF-8: `chcp 65001`.

## 5. Подводные камни этого репозитория

Собраны по ходу работы, стоят внимания:

- **Движковый код непереносим и не является библиотекой.** `Model/lwExpObj.h`
  тянет `lwDirectX.h` и `stdafx.h`, `Map/SceneFileLoaders.h` — `d3dx9math.h`.
  Подключать `sources/Libraries/DirectX/include` на x64 нельзя (ошибка C2733).
  Исходники движка используются **только как спецификация формата**.
- **Имена текстур в моделях не совпадают с файлами.** Модели ссылаются на
  `.BMP`, на диске лежат `.png`. Резолвить по имени без расширения.
- **В `.lgo` три разные раскладки блоков** (версии `0x0000`, `0x1000..0x1003`,
  `0x1004+`), и у легаси-версии вложенная версия лежит в начале **каждого**
  блока. В `.lmo` эту вложенную версию читает только запись геометрии — helper
  читает свою сам.
- **Данные бывают грязными.** У `garner.map` в конце тела 8 блоков, на которые не
  ссылается ни одна секция. Кратность размеров секции не требуется: движок делит
  нацело (`room.map` — 52×52 при секции 8×8 даёт сетку 48×48).
- **Правило проекта: без `try`/`catch`** без явного согласования. Ошибки —
  возвращаемыми статусами.
- **`.rc`-файлы** ломаются Edit-инструментом (кодировка GBK) — править через
  `sed -i`.

## 6. Главный инвариант, который стоит сохранить

Все парсеры конвертера построены на одном правиле: **каждый блок обязан
прочитать ровно объявленное для него число байт**. Это строже проверки в
оригинальном `LgoLoader::LoadEx`, которая сверяет только итог по файлу.

Именно этот инвариант нашёл все различия между версиями формата: там, где парсер
расходился с объявленным размером хотя бы на байт, обнаруживалась целая новая
раскладка. Если будете добавлять форматы — сохраните это правило, оно
превращает пакетный прогон в формальную верификацию.
